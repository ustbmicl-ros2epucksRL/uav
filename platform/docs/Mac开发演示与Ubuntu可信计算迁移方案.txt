2026-11-16 实现更新：平台已接入 demo / hardware 双模式，硬件路径通过 Trustee 取钥，Mac 已具备软件联调测试。下文为 11 月 13 日基线与迁移规划。当前部署以《平台密钥模式与远程证明接入.txt》为准，实机证明、防宿主 root 验收及存量密钥迁移仍待完成。

Mac 开发演示与 Ubuntu 可信计算迁移方案
版本：2026-11-13；性质：当前能力盘点、后续实施计划及待执行验收规范

一、结论与推进方式
继续在当前 Mac 上完成业务开发、功能演示、协议联调和软件安全回归，无需现在更换电脑。以后由 Mac 通过浏览器、SSH 和构建流水线操作 Ubuntu 可信计算服务器。
Ubuntu 是部署载体，不是硬件安全能力本身。普通 Ubuntu 主机、Mac 上的 Ubuntu 虚拟机和 Docker 均不能自动提供本项目要求的宿主 root 隔离。后续选用具备 AMD SEV-SNP 或 Intel TDX 的机密虚拟机路线，先验收 CPU 可信执行闭环；GPU 作为独立后续阶段。两条 CPU 路线择一，不要求同时采购。当前 Python/FastAPI 整体迁移适合机密虚拟机路线；SGX enclave 不是现有应用的直接替换部署方式。
本次仅整理实施文档，没有迁移正式数据库、重置检查点或宣称完成硬件证明。

二、四个核心模块的实际状态
1. 数据安全柜
已实现：容器模板注册、审核、发布和不可变版本；图片/视频附件绑定；AES-GCM 加密；1 MiB 分块上传；暂停、断点续传；S3 独立密文存储；Range 预览；旧 SQLite 附件及跨对象存储迁移。
已验证：真实 SeaweedFS 4.52 原生进程的 HTTPS、持久数据目录、条件写入、匿名访问拒绝、平台删除权限拒绝；约 12 MB 合成视频上传和播放、故障恢复。
未验证：正式生产对象桶、多节点高可用、长时间压力、2 GiB 文件全流程实测。2 GiB 是配置上限，不是实测容量结论。Compose 配置语法已校验，Docker 容器启动未实测。

2. 防 root 窃取与授权状态保护
已实现：全数据库状态认证、独立 HTTPS 检查点和 CAS；篡改/旧状态恢复/检查点不可用时拒绝；分块清单、身份、授权、模板与审计均纳入状态保护。
适用边界：这些软件测试验证的是状态与密文攻击的检测逻辑，依赖状态认证密钥、独立检查点及运行代码处在可信域。不能据此宣称当前 Mac 平台能抵御已掌握本地密钥、修改运行代码或读取内存的宿主 root。
已有研究组件：Trustee KBS 客户端适配器、独立 KBS/AS/RVPS 部署生成器、策略生成器与 attested_smoke.py。
尚未完成：真实 SNP/TDX 证明、厂商证书链/TCB 验证、硬件密钥释放、受度量平台完整闭环及宿主 root 攻击验收。
代码依据：platform/app/cabinet_persistence.py 当前 open_cabinet() 明确使用 LocalDemoBroker，KEK、审计等密钥由 guard.key 派生。platform/app/cabinet_auth.py 的账号凭据加密和 CSRF 也依赖该派生路径。仅存在 trustee_broker.py 不代表平台已经接入硬件 KBS。

3. 一份数据多主体授权使用
已实现：真实用户登录、组织与角色管理；同一资产对 A/B 分别授予用途；独立 preview 权限；额度、到期、撤销；跨主体隔离；预览会话绑定登录和账号版本，每次 Range 重新校验。
当前定位：可演示“同一份数据对不同主体授权使用”，尚不是带合同、计费、结算与争议处理的完整商业交易系统。
边界：撤销阻止后续读取，无法追回已经返回浏览器的明文，也不能自动撤销已释放的密钥。已有一个通过鉴权并开始返回的有界响应可能继续传输。后续任务、计算进程和密钥租约须单独设计撤销语义。

4. 模型可用数据生成
已实现：受模板约束的数值表转换、统计汇总、样本分组拆分、来源/模板版本记录；示例数据标为合成。
未实现或未验收：真实低空数据端到端采集、影像自动标注/视频帧特征流水线、生产质量评价，以及 CPU/GPU 可信训练推理。附件能入柜和播放，不等于附件已转为高质量训练集。

当前证据：既有回归 81 项通过、真实对象服务集成累计 7 项通过；6 项外部 OPA 依赖测试跳过，另有 20 个子测试通过。该记录对应前两轮代码验收，本次文档整理未重复运行全部测试。所有结果均为开发/合成数据验证，不是外场指标或硬件安全认证。

三、目标系统与信任边界
Mac 浏览器 / 受信采集端
  → 端到端认证与 TLS
  → Ubuntu 机密虚拟机：身份与用途授权、模板检查、入柜加密、解密预览、模型数据加工、审计与检查点客户端
      → 独立信任域：Trustee KBS、AS、RVPS；独立检查点服务
      → 独立对象服务：只保存经过认证的密文

需要防范的是计算宿主/虚拟化层 root。机密虚拟机内客体内核与应用仍属于可信计算基；客体 root、应用漏洞、浏览器端、采集端、独立密钥服务管理员不能一概视为已被 CPU TEE 防护。
独立信任服务不得与计算宿主共享管理员权限、密钥卷或可被一起回滚的备份。仅把两个容器放在同一 root 管理的宿主上，不构成此处的独立信任域。KBS 的 root 当前仍受信；如要求防范该管理员，需要额外 HSM/KMS、审批和密钥管理设计。
TLS 明文终点必须在可信采集端/机密虚拟机内。宿主机 nginx 若终止 TLS 后转发明文，会破坏防宿主窃取目标；外层仅做透传或采用已经证明的端到端加密方案。不能将明文附件、密码、密钥或中间特征写入宿主共享卷、日志、core dump 或未保护的交换区。
TPM 2.0 可辅助启动度量与密钥封装，但不能单独保护普通进程解密后的内存。CPU 机密虚拟机也不自动保护普通 GPU 的显存与传输链路。

四、硬件与软件准备条件
A. CPU 可信计算节点（选择一条路线）
AMD 路线：供应商明确支持 SEV-SNP 的服务器/机密云实例，匹配的 BIOS/安全固件、宿主内核、KVM/QEMU/固件及客体；能实际生成 SNP 报告，由独立验证端验证证书链、安全版本和度量。
Intel 路线：供应商明确支持 TDX 的服务器/机密云实例，匹配的 BIOS、微码、TDX module/SEAM、VMM、客体和 quote 获取/验证链；能实际生成并验证 TDX quote。
采购条件不是“某代 CPU”这一项，而是整机/云 SKU、固件与软件栈的兼容性和可验收证明。让供应商提供精确型号、启用状态、安全补丁基线、报告/quote 样例及失败反例。普通云 VM 和嵌套 Ubuntu VM 不能默认视为机密实例。

B. 独立信任节点
单独管理域的 Linux 服务节点部署 KBS/AS/RVPS 与检查点，具备可靠持久盘、TLS、可信时间、参考值管理、厂商背书/吊销资料获取和备份权限隔离。证明资料不可用时按策略拒绝，不能自动关闭验证。

C. 对象存储节点
可部署已有 SeaweedFS 或兼容 S3，要求有效 HTTPS、条件写入、私有桶、前缀最小权限、持久化与恢复。单节点可用于第一期，但生产冗余、容量和恢复目标需另外验收。

D. 首期资源预算（工程起点，不是硬件厂商最低要求或实测性能承诺）
机密虚拟机先按 8 vCPU、32 GiB 内存规划；独立信任节点先按 4 vCPU、8 GiB 内存规划；对象服务独立数据盘根据保留期和密文容量计算。先使用 CPU 和合成数据，不把 GPU 列为第一期必需采购。带宽、磁盘空间和并发度在负载基准后调整。

E. Ubuntu 与版本冻结
选择供应商和云服务明确支持的 Ubuntu LTS 主客体组合。以正式支持矩阵确认宿主内核、虚拟化栈、固件和客体驱动，不仅检查 Ubuntu 发行版号。云实例用户通常不管理宿主，应由厂商提供相应证据和支持范围。
记录 BIOS/固件/微码、宿主内核、QEMU/OVMF、客体镜像摘要、kbs-client 哈希、Trustee 提交与策略摘要；设定最低允许 TCB 和补丁更新流程。现有研究目录中的版本是接口兼容基线，不能照抄成未来采购或安全修复基线。官方资料核对日期见末尾。

五、继续在 Mac 上推进的工作
第一阶段：保持现有运行环境，以隔离 SENSE_DATA_DIR 和合成账号演示四个核心模块；真实 SeaweedFS 原生模式用于对象服务联调。继续补业务数据模板、模型转换和用户体验，不开启假证明模式。
第二阶段：将配置按“业务配置、对象存储配置、检查点配置、未来证明配置”分开管理；密钥不进入仓库和演示材料；保持软件演示与硬件证明的状态标识清晰。
第三阶段：为 Ubuntu 构建可重复部署包，记录 Python 依赖、客户端/应用摘要和验证结果。Mac 若为 ARM，不能直接把 macOS 二进制或虚拟环境复制到 Linux x86_64；在目标架构 Linux 构建环境重新构建并验证。
第四阶段：用同一 API 和测试集接入远程测试节点，Mac 继续作为开发/演示终端。没有硬件时，可以完成协议失败关闭测试，但硬件报告字段一律保持“未验证”。
执行入口仍采用现有脚本，详见 README.txt、真实对象存储部署与迁移验收.txt；本计划不创建新的未验证生产部署入口。

六、迁移到 Ubuntu 的分阶段实施步骤
阶段 0：冻结基线与数据分类
冻结当前代码和测试结果；列明资产、模板版本、授权、对象清单、检查点 namespace/head 及恢复策略。划分合成数据和真实数据。第一轮使用全新的合成试验命名空间，不接触原正式状态，不使用重置检查点作为故障修复手段。
交付：版本清单、数据清单、威胁模型、验收负责人和独立管理员分工。

阶段 1：准备硬件与机密虚拟机
按 SNP 或 TDX 官方/OEM 路线启用硬件、更新补丁、部署受支持的 Ubuntu 主客体。验证机密实例属性，实际获取报告/quote，保存脱敏证据。设备节点存在或日志中的 tee=true 不算验收。
交付：硬件型号与版本矩阵、真实证据、厂商链验证结果。

阶段 2：独立信任服务先行
在独立管理域运行 KBS/AS/RVPS 和检查点；沿用 research/data_security_cabinet 中 prepare_trustee.py、prepare_checkpoint.py 等生成器并对目标版本复核。先保持 deny-all，再从受控构建建立参考值；不得把未知客体自报值直接登记为可信基线。
验证 KBS TLS、验证端背书资料、资源策略与参考值；管理员入口仅对管理网开放。先证明错误环境拿不到密钥，再开放批准环境。
交付：固定策略、参考值来源、密钥资源目录、审计与备份方案。

阶段 3：完成平台密钥与可信边界改造（当前尚未完成）
把 platform/app/cabinet_persistence.py 的 LocalDemoBroker 路径替换为真实证明后的密钥提供；硬件模式缺少证明必须启动/请求失败，禁止回退本地演示密钥。
不仅替换附件 KEK：audit、operator、state、checkpoint token、账号凭据加密和 CSRF 派生所依赖的秘密都必须通过独立可信渠道进入机密虚拟机，不能仍放在宿主可读配置文件。区分 bootstrap 所需凭据和普通业务会话，避免“先有本地根密钥才能证明”的循环。
把登录验证、主体授权、模板策略和状态校验与解密计算一起放入可信域，不能仅把一个解密函数移入 TEE 后继续相信宿主提交的“已授权”标记。
固化客体镜像、应用、CA、证明客户端、启动参数与策略；禁用不受控 exec、调试和明文共享路径。量测必须覆盖实际工作负载和配置，不能只核对 CPU 类型。
现有 attested_smoke.py 只用于研究核心的真实 KBS 连通试验，不替代平台登录/组织/模板/分块/撤销完整验收。现有 KBS 适配器提供执行器级 KEK，尚不代表 KBS 已实现逐用户逐任务的交易裁决；若要求后者，需要独立授权票据与证明通道绑定扩展。
交付：真实硬件模式的完整平台路径、秘密生命周期和无降级测试。

阶段 4：迁移状态与密文
在可信域中执行既有迁移工具，先预检/报告，再 apply，逐块核验后切换；参见真实对象存储部署与迁移验收.txt。
旧 Mac 演示 KEK、状态认证密钥及其派生秘密曾位于普通环境，复制到 TEE 不会使历史数据追溯获得硬件保护。第一期可用全新可信密钥处理新合成数据。
正式旧数据迁移还需额外实现和验收密钥版本化/重封装：在受控可信迁移端解封旧 DEK、以新 KBS KEK 重封装；逐项处理审计/账号/状态密钥依赖，设计保持检查点连续性的切换协议，不能直接改 state.key 导致全部状态失配，不能重置 head 来绕过校验。当前对象迁移命令只搬密文或重新分块，不实现上述硬件密钥升级。
交付：保持撤销与额度的迁移报告、新密钥版本、可恢复且不复活旧权限的切换方案。此项是正式存量迁移的上线门槛。

阶段 5：验收与灰度
先跑真实证明正反例，再跑业务闭环、重启、断网、对象篡改、数据库回滚和宿主攻击测试；记录资源占用与性能。仅对通过门槛的环境标为“已通过硬件验收”。生产灰度前审查证书续期、补丁、镜像更新参考值审批、灾备和运维权限。

七、验收指标与证据（以下为计划，不是已测成绩）
H01 平台身份：精确硬件/云 SKU、固件和软件版本清单完整；同一证据可由独立验证端验证。仅主机自报不通过。
H02 正常证明与取钥：批准镜像、参考值及平台状态下，连续 20 次新鲜证明和受限密钥获取成功；保留脱敏验证日志、策略版本和请求关联号，不保存密钥明文。
H03 反例拒绝：非 TEE、未批准镜像/应用、被改启动配置、调试状态、过低 TCB、错误 CA、伪造/重放证据和证明服务不可用，每类至少 20 次测试，未授权密钥释放为 0；后端不可通过 demo broker 继续运行。具体反例按所选 TEE 支持方式实施并注明不可测试项。
H04 通道与秘密：证明绑定新鲜挑战和会话公钥；密钥仅进入批准可信执行器。对宿主共享卷、代理日志、临时文件、core dump 和对象目录扫描，不出现预置明文标记或测试密钥；保留扫描范围与方法。
H05 宿主 root：在授权隔离测试机上，以宿主 root 尝试读取来宾内存/调试接口、替换启动镜像和挂载共享文件。不得取得测试秘密；启动篡改必须导致证明拒绝。单次内存扫描未发现标记不足以单独证明安全，需同时提供硬件证明、隔离配置及攻击覆盖证据。不把客体 root 攻击纳入已覆盖结论。
H06 跨主体与用途：A 的 preview 可用，B 只有 stats 时原附件/流 ID/分块读取均拒绝；跨账号、组织禁用、角色变化、模板停用等负例每类至少 20 次，越权明文返回为 0。
H07 撤销：以撤销提交成功为线性化时点，随后发起的原登录/旧流 ID/任意 Range 请求不得返回新明文；并发至少 20 轮，记录在途响应边界。前端清空时间目标不超过 10 秒，仅作体验指标，不替代后端拒绝。长任务终止和密钥租约另验，不能用此项声称追回已交付数据。
H08 防回滚：保留独立最新检查点，恢复授权撤销前、模板变更前或上传取消前的旧数据库；操作应拒绝且无明文释放。篡改清单、调换/截断密文同样拒绝。恢复整个机密 VM 快照也必须触发外部新鲜性检查，不因内存中的旧会话绕过。现有软件测试未完成真实 VM 快照攻击验收。
H09 持久化与网络：选 12 MiB、256 MiB 和 2 GiB 三档合成视频/附件，逐档验证中断、平台重启、对象服务重启、断网恢复、续传摘要及跨块 Range；全部重建字节摘要一致，重复块不被覆盖。2 GiB 档需实机执行后才能宣称支持该规模已验收。
H10 迁移连续性：原资产/附件/授权标识、撤销状态、已用额度、模板版本与未完成会话保留；目标冲突不得覆盖，失败不得错误切换。另验新旧密钥版本切换、废弃旧密钥后的访问行为和灾备，不允许恢复旧撤销状态。
H11 性能：在同硬件、同数据、同网络下比较受支持的非机密基线与机密环境；分别记录证明/取钥耗时、上传吞吐、首帧时延、Range P50/P95、CPU、内存和密文存储放大。先给出测量结果，再约定 SLA。不得把早期“性能/存储开销不超过 1%”写成已达到指标；AEAD 标签、密钥封装、清单和审计均存在开销。
H12 运维：TLS 到期/CA 错误、密钥服务故障、检查点故障均失败关闭；配置恢复后可恢复正常访问，不能重建 namespace 跳过状态验证。参考值更新与密钥轮换有独立审批和可追溯记录。

所有硬件验收项当前状态均为“待执行”。最终报告应逐项记录环境版本、输入规模、步骤、预期/实际结果、证据路径、执行人和遗留问题；负例有未覆盖项时不得给出“全量通过”结论。

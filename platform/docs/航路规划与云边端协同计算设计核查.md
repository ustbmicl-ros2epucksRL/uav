# 航路规划与云边端协同计算：系统设计核查

日期：2026-11-13  
依据：当前前后端代码静态检查及用户明确的系统目标。本文区分已实现能力与建议设计，不将建议接口或算法表述为已经实现。

## 1. 系统核心定位

本系统的核心是**低空航路规划、云边端协同计算算法的实现、可视化与仿真验证**。

应形成“区域与约束建模 → 航路计算 → 云边端资源配置与任务卸载 → 联合指标评估 → 仿真执行与回放”的主流程。资源审批、监管、地面站、SITL 和飞行档案是配套的业务与执行验证模块，不能取代算法主线。

保持一个系统、一个入口和当前三列地图布局。需要调整的是功能优先级与面板内容，不是再建设一个独立产品。

### 2.1 不能混同的概念

- 给定航路的感知覆盖评估，不等于生成航路。
- 感知设备布设优化，不等于云边端计算资源部署与卸载优化。
- 感知模型的 SINR/可见性，不应未经链路定义与标定直接当作通信吞吐量。
- 单机后台队列，不等于跨云端、边缘和机载设备的分布式计算。
- 生成 `simulated_ack`，不等于远端任务已经执行。
- 三维飞机回放，不等于算法决策过程可视化。

### 2.2 当前页面的主要偏差

1. 首页及主流程更突出地面站、飞行控制、巡检、审批和档案，算法入口偏深。
2. 航线生成、感知覆盖、感知部署和调度分散在不同模块，用户难以围绕同一个问题连续操作。
3. 云边端资源模型尚未建立，当前调度无法回答“为什么卸载到该节点”“耗时多少”“链路断开后如何重分配”。
4. 运行结果主要是路线、飞机运动或 JSON，缺少算法基线对比、代价分解和约束失败解释。
5. 业务任务与飞行档案虽已关联，算法实验、路线方案、计算调度方案尚未形成统一关联链。

## 4. 航路规划算法设计

### 4.1 输入与输出

输入包括区域坐标基准、起终点/途经点、建筑及禁飞区、飞行高度范围、安全间隔、速度和电池约束。多机时间窗、通信质量、计算任务需求作为后续扩展字段。

输出应包括：

- 路线三维点及可选的预计到达时间；
- 可行性和违反的约束；
- 路程、预计耗时、能耗估计、风险或通信指标；
- 候选方案与选定依据；
- 场景版本、算法版本、参数和运行耗时。

### 4.2 实施顺序

1. 将现有定高 A* 和安全复核接到统一算法入口，保留原结果与限制说明。
2. 增加多高度候选比较，统一评价距离、时间和约束；不能把独立高度比较直接称为完整三维最优搜索。
3. 明确定义通信模型后，增加通信约束或通信代价，并展示沿程指标。
4. 再引入动态禁飞区、时间窗、多机间隔及滚动重规划。

可采用归一化的多目标代价：路线距离、时间、能耗、风险和断链代价的加权组合。权重需记录，硬约束不得通过调整权重被绕过。输出应明确“该模型和候选范围内的结果”，不宣称全局最优。

## 5. 云边端协同计算算法设计

### 5.1 必须补齐的数据模型

| 对象 | 必需字段示例 |
| --- | --- |
| 端节点 | 飞机/任务机标识、可用 CPU/GPU、内存、电量、位置、在线状态 |
| 边缘节点 | 地理位置、资源容量、覆盖或连接关系、队列状态、服务类型 |
| 云节点 | 可用计算资源、接入路径、基础时延、费用模型 |
| 通信链路 | 端点、可用吞吐量、传播/协议时延、可用性、时间变化 |
| 计算任务 | 输入/输出数据量、计算工作量、截止时间、依赖、优先级、可执行节点 |
| 调度决策 | 分配节点、开始/结束时间、资源分配、传输路径、失败或迁移原因 |

所有量必须有明确单位。计算工作量采用 cycles、FLOPs 或经过标定的耗时之一，并与节点服务能力使用一致口径，不能把当前无固定单位的 `compute` 直接当作真实算力。

### 5.2 第一阶段算法

先建立离散事件仿真和确定性的可解释基线：

- 全部在端侧执行；
- 固定分配到边缘或云；
- 选择可连接且满足约束的节点；
- 按优先级/截止时间，选择预计完成时间最早的可行节点。

预计完成时间至少拆分为：上行传输、链路时延、节点排队、计算、下行结果返回。计算资源容量、并发、内存、任务依赖和截止时间作为约束。无可行节点时明确返回失败或排队，不能生成成功回执。

可视化必须来自算法输出的事件和指标，不使用与求解无关的动画流线代替真实决策。

### 5.3 仿真和真实执行分层

第一阶段的“云边端”是明确标注的仿真节点。以后接入真实任务机、边缘服务器和云 Worker 时，需要增加注册、心跳、任务协议、执行回执、结果校验和失败重试机制。

本机持久化计算队列可复用为实验任务管理，但不能仅修改节点名称就宣称完成了真实分布式执行。

## 6. 航路与计算协同

第一版可采用可解释的分阶段联合评估：

1. 在相同场景与约束下生成若干可行候选航路。
2. 根据路线位置和预计时间生成通信连接序列。
3. 对每条候选航路运行同一组计算调度基线。
4. 比较任务完成率、超时率、端到端时延、飞行及计算能耗、链路中断和节点利用率。
5. 选择满足硬约束的方案；无可行方案时展示原因和可调整参数。

这是候选方案范围内的联合评估，不是已经实现的联合优化算法。后续再研究滚动规划、迁移开销及更复杂的求解方法。

## 7. 前后端与已有执行链衔接

建议新增明确的算法领域模块，而不是继续向地面站控制脚本叠加求解逻辑：

- 场景快照：统一空间约束、通信假设、算力节点与任务需求。
- 航路求解：复用并扩展现有航线基线。
- 协同计算：资源、链路、任务模型和调度器。
- 联合评估：候选路线与计算策略对比。
- 实验记录：参数、代码版本、种子、输入快照、求解结果和可视化事件。

建议关联链为：

```text
experiment_id
  ├─ scene_revision / algorithm_version / parameters
  ├─ route_plan_id
  ├─ compute_schedule_id
  ├─ evaluation_result
  └─ business_task_id → execution_id → record_id
```

前四项是需补齐的算法上下文；后三项已有业务执行关联基础。算法实验成功不自动授权飞行，只有通过执行前复核的方案才进入既有任务准备和 SITL 控制流程。

## 8. 验收标准

- 同一输入和随机种子可复现实验，参数和算法版本可追溯。
- 算法返回的路线与地图绘制点一致，安全约束检查结果可解释。
- 算力容量、链路时延和任务截止时间的变化真实影响分配结果。
- 节点离线、链路中断、资源不足、无可行航路时有明确失败结果。
- 时延分项与总时延一致；节点并发不能超出模型容量；依赖任务不能提前执行。
- 基线比较使用相同任务、场景、种子和指标定义，不把模型估计值当成实测性能。
- 可以沿时间轴同步查看飞机位置、任务所在节点、传输/排队/计算阶段和结果返回。
- 既有 SITL 任务与回放继续可用，算法实验记录能定位其后续执行档案。

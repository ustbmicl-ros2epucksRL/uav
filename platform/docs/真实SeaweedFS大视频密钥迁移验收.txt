在 platform 目录运行 scripts/accept_seaweed_key_migration.sh。脚本使用 PATH 中的 python3、weed、ffmpeg 和 ffprobe。也可明确指定已有 Python 环境及二进制，例如本次 Mac 环境使用

Ubuntu 准备
安装支持项目依赖的 Python 3.11+、venv 和包含 libx264 的 ffmpeg。准备目标 Ubuntu 架构的 SeaweedFS 4.52 可执行文件，在 platform 下执行
  python3 -m venv /tmp/cabinet-acceptance
  /tmp/cabinet-acceptance/bin/python -m pip install -r requirements-dev.txt
  SENSE_PYTHON=/tmp/cabinet-acceptance/bin/python CABINET_WEED_BINARY=/opt/seaweedfs/weed bash scripts/accept_seaweed_key_migration.sh
本机需要可用的回环 TCP 端口和可写临时盘。Mac 脚本用 hdiutil 挂载容量上限为 2 GiB 的临时稀疏卷，实际占用随写入增长，结束后卸载并清理。这样 SeaweedFS 可按独立测试卷的可用空间计算容量。Ubuntu 使用 pytest 临时目录，所在磁盘应能通过 SeaweedFS 的容量检查。验收使用临时数据库、独立 HTTPS 检查点和真实 SeaweedFS 本地进程，共用现有测试服务夹具。测试账号、CA 与密钥在测试期间生成。脚本不需要管理员权限。终端以 pytest 退出码报告成败。

演练流程与通过条件
1. 生成超过 8 MiB 的 H.264 合成视频。第 0 块提交后实际停掉对象服务；下一块请求应返回 503，服务器确认清单仍只有第 0 块。重启相同数据目录，从第 1 块续传并完成入柜。
2. 对同一视频资产给两个具有预览角色的主体分别授权。两人各开启一次预览，所有者撤销其中一人的权限。保存全部授权行、各真实对象键、密文 SHA-256 和原 DEK 信封用于核对。
3. 通过平台离线管理入口迁移。受控注入“远端已提交新摘要和新 token，但客户端丢失响应”。此时旧数据库仍在原路径，旧 token 已失效。原命令重跑，从与最新检查点相符的候选库恢复。再次执行检验幂等。
4. 核对每块对象键与直接从 SeaweedFS 读取的密文摘要均相同，每块信封均变化。核对所有授权行完全相同，包括主体、用途、撤销标志、到期时间、额度和已用次数。
5. 原登录 cookie 访问返回 401。主体重新登录后，原流会话继续被拒。已撤销主体新开预览返回 403。有效主体剩余 4 次，可开启一次预览并逐段通过 HTTP 206 读取完整视频，拼接的 SHA-256 必须与上传源一致；再开启预览 3 次成功，下一次返回 403。
6. 迁移前拒绝取钥时，数据库应逐字节保持原样。迁移后分别将放行条件切换为要求 SNP 声明（当前客户端提供 sample 声明）和停掉 KBS，已有视频流的 Range 请求及身份接口应返回 503。恢复 KBS 和测试策略后方可继续读取。
7. 在临时库恢复演练前的 SQLite 快照。线上读取返回 409，离线迁移也拒绝将旧库重新登记。最终输出视频字节数、块数、完整摘要及刚切换时的剩余额度。

Ubuntu 硬件环境的正式切换
一键脚本用于部署前的软件演练。验收入口启动独立的 Trustee KBS，使用内置 AS 和 RVPS。管理客户端负责登记资源及发布策略，读取客户端通过 TLS 和 sample 证明获取密钥。默认使用固定提交 22ca43188fb2db632d43d3d5a164e0edbd5ab021，需准备 Docker、Git 和该提交对应的 kbs、kbs-client-image 镜像。离线复验可设置 CABINET_TRUSTEE_SOURCE 指向该提交的干净源码并预载两个镜像。容器在独立内部网络通信。策略仅允许测试命名空间的五个合成资源。正式 Ubuntu 部署必须使用与机密来宾硬件和受信度量匹配的策略、原生客户端及独立 KBS 管理域。请勿把 sample 策略、Docker 客户端桥接脚本或测试密钥复制到生产配置。Ubuntu 实机签发证明、KBS 拒绝不合格度量、浏览器播放及真实断电需另行验证。
在机密来宾内配置主机匹配的 kbs-client、受信 CA 和客户端摘要。KBS 中准备同 namespace 的新 state-v1、operator-v1、audit-v1、kek-v1、checkpoint-v1。检查点支持 /v1/rotate。保留同一检查点 URL、namespace 和已有对象桶。停平台、备份、确认临时盘可容纳数据库副本，然后以真实配置执行
  export SENSE_CABINET_KEY_MODE=hardware
  export SENSE_CABINET_ATTESTATION_CONFIG=/etc/cabinet/hardware.json
  export SENSE_CABINET_OBJECT_CONFIG=/etc/cabinet/objects.json
  export SENSE_DATA_DIR=/var/lib/cabinet
  python -m app.cabinet_admin check-objects --probe
  python -m app.cabinet_admin migrate-demo-keys --source-checkpoint /run/cabinet-migration/old-checkpoint.json
中断后保持服务停机，保留活动库与 hardware-migration.pending.db，原样重跑迁移命令。恢复后通过 /api/cabinet/me 验证远程取钥及登录状态，再复核授权与用量、预览和审计。独立检查点应保持最新版本。离线恢复旧状态只能在隔离验收副本中演练。完整密钥供应、秘密保留期及升级步骤见《平台密钥模式与远程证明接入.txt》和《真实对象存储部署与迁移验收.txt》。

Ubuntu SNP / TDX 来宾一键验收（仅隔离验收环境）
默认 --mode sample 继续使用 Docker 中的测试 KBS。--mode snp 或 --mode tdx 调用来宾内原生 kbs-client 和已有独立 Trustee。平台业务 API、真实本地 SeaweedFS 和临时 HTTPS 检查点运行在来宾内。此流程验证取钥及迁移；生产拓扑中的异机检查点、外部存储网络和浏览器播放需单独复核。

1. 创建 x86_64 Ubuntu 机密来宾。SNP 检查 /dev/sev-guest，TDX 检查 /dev/tdx_guest 或 /dev/tdx-guest，也支持具有报告目录写权限的 configfs TSM 接口。准备与来宾架构匹配的原生 ELF kbs-client，按批准构建清单获取其 SHA-256。设备接口只作预检；实际 TEE 类型和启动度量以独立服务验证记录为准。安装上文 Python、SeaweedFS、ffmpeg、ffprobe 依赖。批准策略应绑定工作负载、启动度量、TCB、安全状态和调试位。
2. 准备专用 KBS 和 platform-test 命名空间，供应五个测试资源。按 platform/deploy/cabinet-keys/hardware.example.json 填写 KBS HTTPS 地址、信任 CA、客户端绝对路径及摘要，namespace 设为 platform-test。验收自动使用新建检查点覆盖配置副本的 checkpoint_url 及 checkpoint_ca_file。测试会创建演示源库并迁移，不能复用正式 KBS 的管理面、资源或检查点。独立端先准备两份资源策略，可使用 research/data_security_cabinet/render_resource_policy.py。两份策略只改变 SNP measurement 或 TDX MRTD 的 48 字节参考值，其余资源路径、init-data、调试约束和 AS/RVPS 配置保持一致。批准值来自受控构建。负例在同一实机来宾上检验参考值不匹配，另一个来宾镜像的启动测试需要另外执行。
3. 配置独立控制端。脚本随附 scripts/cabinet_qa_controller_ssh.sh，使用已固定主机公钥的 SSH 别名 cabinet-qa-control。SSH 密钥仅准调用专用测试环境的强制命令。站点须对接自己的 KBS 服务管理器、策略发布和 AS/KBS 审计源；KBS 管理令牌仅留在独立管理域。可用 --controller 指定等价的可执行适配器。适配器收到三个位置参数 ACTION TEE RUN_ID，每次有 120 秒超时，失败退出非零。
   approved 发布批准策略并等待 KBS HTTPS 就绪；mismatch 发布只有启动度量参考值不同的策略，保持 KBS 在线；offline 从来宾侧实际断开到专用 KBS 的 TCP 连接，保持控制通道和检查点可用；restore 幂等恢复本轮之前的网络与策略，提交确认后返回。控制端按 RUN_ID 锁定专用实例，在批准/不匹配阶段切换时记录审计游标。来宾失联时由控制端租约超时恢复。
   observe-approved 和 observe-denied 从切换后的权威事件中取出此来宾、此命名空间、此运行的真实资源放行/拒绝记录。等待新事件，校验 AS 签名、有效期及审计关联，将启动测量值和实际策略参考值标准化为 96 位小写十六进制。向 stdout 输出单行 JSON，字段为 run_id、tee、namespace、decision（approved 或 denied）、measurement、reference、event_id。其他动作仅看退出码。事件 ID 使用字母、数字、点、下划线和短横线。缺少归属、签名或实际策略决策信息时应失败；不能由来宾配置或预期结果拼装事件。独立审计适配是部署方需要完成的接口。
4. 从 platform 执行（TDX 将 snp 替换为 tdx）
  SENSE_PYTHON=/tmp/cabinet-acceptance/bin/python CABINET_WEED_BINARY=/opt/seaweedfs/weed bash scripts/accept_seaweed_key_migration.sh --mode snp --config /etc/cabinet/qa-hardware.json --controller "$PWD/scripts/cabinet_qa_controller_ssh.sh" --report /var/tmp/cabinet-snp-run01.json
   --report 使用新的文件名；默认写入 platform/outputs 下的带 UTC 时间戳 JSON。可将报告与独立端对应 event_id 的原始审计记录归档。报告不包含资源、会话 cookie 或证明 token。
5. 验收通过要求。批准度量取钥并完成存量密钥重封装，策略不匹配及 KBS 离线时身份和已打开的 Range 均返回 503；恢复每种故障后已有授权可预览。完整视频摘要、额度、撤销和旧快照拒绝全部通过。已跳过的测试、缺少阶段证据或失败的环境恢复均不能报告 passed。pending 表示本轮未取得该阶段证据。报告的 sample 成绩仅对应 Mac 软件演练。SNP 与 TDX 分别留存真实报告，另外复核宿主 root 隔离、异常断电及实网拓扑。

独立端 systemd 参考实现
随附 scripts/cabinet_qa_control_host.py，可作为上述 SSH 强制命令。专用 KBS 作为独立 systemd service，控制账号仅获准启停该测试单元和更新该 KBS 的策略。将来宾 SSH 公钥限定为 restrict,command="/usr/bin/python3 /opt/cabinet-qa/cabinet_qa_control_host.py"。控制端准备私有可写目录 /var/lib/cabinet-qa-control，并准备权限受限的 /etc/cabinet-qa/control.json，例如
  {"tee":"snp","unit":"trustee-qa.service","guest_id":"qa-snp-01","client":"/usr/local/bin/kbs-client","url":"https://qa-kbs.internal:8443","ca_file":"/etc/cabinet-qa/ca.pem","admin_token_file":"/run/cabinet-qa/admin-token","policies":{"approved":"/etc/cabinet-qa/approved.rego","mismatch":"/etc/cabinet-qa/mismatch.rego","restore":"/etc/cabinet-qa/baseline.rego"},"audit_jsonl":"/var/log/cabinet-qa/verified-events.jsonl"}
独立端审计导出需把真实 AS/KBS 关联事件追加至 audit_jsonl，包含前述字段（run_id 由控制端关联），另含 guest_id 和 resource（例如 state-v1）。独占运行和阶段游标限定审计范围。日志流需在取钥响应后及时落盘，单次验收期间保持文件不轮转。原始 Trustee 日志并非该 JSONL 格式，须按站点审计链对接。专用实例验收前保持在线且加载 baseline.rego。若来宾强制断电导致清理中断，控制端保留 active 租约，运维可用原 RUN_ID 调用 restore，再启动下一轮；需无人值守超时恢复时由站点管理器配置租约看门狗。

AS/KBS 原始审计与报告复核
Mac sample 模式在平台放行及拒绝阶段各执行一次独立的原生取钥探针。探针与平台使用同一读取容器、命名空间、策略和 state-v1 资源；放行时另行核对取回的 32 字节与供应值一致。报告中的 ID 对应这两次专用探针，业务视频 Range 的结果由同轮业务断言验证。固定版本启用 attestation_service 及 actix_web::middleware::logger 的 INFO 日志。一次取钥应依次看到资源 GET 401、认证 POST 200、AS sample CPU 验证成功、证明 POST 200、同资源 GET 200 或 403。401 是获取挑战前的首次请求。拒绝样例中 AS 认可 sample 证据，KBS 的 SNP 资源策略拒绝释放密钥。
采集器在隔离实例上截取单个串行请求的窗口，要求来源、资源和顺序一致。有多次请求、未知访问行或缺少验证记录时失败。每个事件保留带 Docker 时间戳的原始日志行至 <报告名>.audit/<event_id>.log。event_id 是完整容器 ID、换行与归档字节的 SHA-256，raw_sha256 是归档字节自身的 SHA-256。这是验收采集器生成的内容标识。容器清理后仍可复核。报告和同名 .audit 目录应一起归档，在 platform 下执行
  python3 scripts/cabinet_trustee_audit.py /绝对路径/验收报告.json
复核会重新解析来源、接口、状态序列、资源和两项摘要。Mac 本地摘要提供内容一致性；独立取证时需把报告和原始记录送到受保护的审计存储。

Ubuntu SNP/TDX 原始记录归档（补充上节独立端配置）
在 /etc/cabinet-qa/control.json 增加 raw_archive，指向独立端只允许审计导出进程写入的原始记录目录。站点导出程序将 AS 验证事件及 KBS 资源策略执行事件的原始字节分别按 SHA-256 命名归档，再追加 verified-events.jsonl；每个事件增加 "raw_records":{"as":"64位小写SHA256","kbs":"64位小写SHA256"}。控制端读出两个归档并重新计算摘要后方可返回事件 ID。来宾报告保留 run_id、namespace、事件 ID 和两个摘要；现场可按 event_id 查索引，再按摘要定位原始记录并用 sha256sum 复核。须保证权威事件与同一次资源请求、来宾和已验签的 AS 结果关联；并发来宾的记录不可单靠时间相邻关联。原始证明与令牌若含敏感材料，应仅在独立受控域保存。普通 INFO 访问记录无法提供 SNP measurement、TDX MRTD 或已签名 EAR；现场需要接入可导出这些权威字段的审计源。Mac 的 sample 档案不替代真实硬件证据。分别在 SNP、TDX 报告中复核一致/不一致的度量和两个原始记录摘要，并验证缺失或被修改的归档会导致验收失败。

业务预览审计（报告 audit_version=2，取代上述 sample 专用探针）
平台在完整附件预览、打开流及读取 Range 三类路由的入口自行生成 X-Cabinet-Preview-ID，并在响应头返回。服务端按请求上下文向固定取钥客户端传递 CABINET_PREVIEW_ID、每次独立生成的 CABINET_KEY_CALL_ID 和 CABINET_KEY_OPERATION。guard 表示打开安全柜时的取钥，unwrap 表示解封数据密钥。多个 Range 属于多条 HTTP 请求，各有自己的 ID。无权访问的请求可能在解封之前结束。KBS 不可达时，可记录取钥调用失败，但没有服务端放行或拒绝事件。
Mac 使用真实业务接口驱动读取容器。采集器在同一专用 KBS 的所有读客户端调用之间加文件锁，按真实调用前后的日志游标归档 AS 验证、KBS 证明及资源状态，并按请求 ID 写调用索引。每个成功的样例 Range 需有对应的 kek-v1 解封事件。报告的 concurrent_previews 保留两个同时提交的请求（所有者与授权主体）的 ID、实际字节范围和解封事件 ID。平台保留原有跨进程状态锁，多个请求可同时抵达，临界区排队执行；证据不包含同一 KBS 对并行取钥的吞吐指标。可用 python3 scripts/cabinet_trustee_audit.py <报告路径> 逐次重算摘要、比对调用索引及查重。离线复核应同时保存报告及同名 .audit 目录。该索引用于演练，若需抵御改写报告和日志的本机管理员，应由独立端保管证据。
Ubuntu 的观察命令增加第四个位置参数 PREVIEW_ID，使用仓库更新后的 SSH 桥和控制端。可信来宾内固定摘要的原生客户端适配器需读取上述三个环境字段，将它们绑定至本次实际取钥会话，经已认证的审计通道送至独立域。上游原生 kbs-client 默认不会自动上报这些变量。站点导出程序须用同一已验证会话的证据与 KBS 资源访问记录建立关联，向原有 JSONL 添加 preview_id、call_id 和 operation。禁止从浏览器采用这些标识或按相邻时间推断归属。成功读取时查找当前 PREVIEW_ID 的 unwrap/kek-v1 放行，策略拒绝时查找当前 PREVIEW_ID 的 guard/state-v1 拒绝，并继续校验原始记录摘要和度量。trace 缺失或归属不符会使验收失败。按上文 snp 和 tdx 命令分别联调站点客户端、导出程序与控制端，复核并发的两个请求 ID、资源策略和原始记录。实机运行和现场适配尚待验证。

真实会话关联与并发验收（audit_version=3）
本版本替代 v2 的逐调用文件锁和日志窗口。Mac 在隔离测试实例上向 127.0.0.1 发布临时 TLS 端口，校验 KBS 的 CA 和主机名。常规管理与非预览读取沿用上游 CLI。预览使用专供 QA 的 RCAR 0.4 sample 客户端。它针对每次调用创建独立会话、挑战和临时 RSA 公钥，将预览 ID、调用 ID、操作和完整资源路径按顺序编码为紧凑 JSON 数组并取 SHA-256，作为合成 sample 证据的 svn。AS 将该声明及 runtime_data 纳入签名 EAR；客户端验证固定 AS 签名、nonce、临时公钥、报告数据与绑定摘要。KBS 的 sample 放行策略核对查询参数中的绑定与已验签声明，放行后向该临时公钥返回 JWE。策略拒绝仍可看到 AS 成功签发及资源读取 403。离线时没有对应的 AS 成功事件。
归档按请求 ID 和调用 ID 精确选取 auth、attest、resource 三条服务器访问记录，资源记录携带会话、挑战、EAR 和签名证明摘要。每个 receipt 保存签名输入摘要及 ES256 签名供离线核验。完整 EAR、会话 cookie、临时私钥和密钥明文仅在进程中使用。离线校验可以重新验证签名摘要、KBS 原始访问行与调用索引。签名声明内容的逐字段核对在真实取钥时进行。报告内公钥归档应与独立信任域的批准 AS 公钥核对。
硬件模式的 Range 请求在进入数据库锁前并行取得本请求所需的远程密钥，取得锁后读取最新检查点并校验授权，读取密文后再次远程取 KEK 解封。合成验收检查两个用户的真实会话从挑战返回到资源响应的单调时钟区间有交集，并检查两个响应的字节范围。状态提交仍通过原来的锁与独立检查点。可用 python3 scripts/cabinet_trustee_audit.py <报告> 离线检查重叠、事件重复和归属。
Ubuntu SNP/TDX 应在可信执行镜像内使用原生硬件证据提供程序。sample 的 svn 是演练字段，不能写入 SNP/TDX 的硬件 SVN。现场适配器应关联经验证的 nonce、临时公钥和硬件 report_data，使用受证明的临时密钥认证包含 preview_id、call_id、operation、资源路径和挑战的绑定记录，并在独立端核验该记录、EAR 签名和 KBS 的实际会话。权威 JSONL 增加 session_sha256 与 ear_sha256 两项，均为 64 位小写十六进制。测试两个用户同时读取不同区间时，应保留同一时钟域的重叠证据。分别在 SNP、TDX 复验绑定互换、错误度量和断网拒绝，保存对应 AS/KBS 原始记录。硬件适配和实机并发性能需现场验证。
存储拓扑的独立矢量图位于 figures/cabinet-storage.pdf，同目录的 cabinet-storage.tex 可由 xelatex 单独编译。
v3 离线签名复核需使用已安装项目 cryptography 依赖的 Python。与一键验收使用同一个虚拟环境，例如在 Mac 上执行 /tmp/cabinet-platform-venv/bin/python scripts/cabinet_trustee_audit.py <报告>。
